# 数据库设计

> 数据库设计不是“画 ER 图”，而是在读写模式、数据增长和一致性之间做取舍。

数据库设计最常见的错误，是先把表画出来，再问“查询怎么优化”。真实设计应该反过来：先看读写模式、数据量、查询方式和一致性要求，再决定表结构、索引、事务边界和是否分片。

一个字段放错表、一个索引顺序反了、一个事务太长，可能在数据量小的时候完全看不出来，等数据涨到亿级才开始付出代价。数据库设计的目标，是让系统在数据增长后仍然可查、可写、可迁移。

## 本章目标

学完本章，你应该能够：

- 根据读写模式设计表结构和索引。
- 判断何时规范化、何时反规范化。
- 选择事务隔离、乐观锁或悲观锁。
- 评估分片、读写分离和迁移方案。

## 先明确读写模式

设计前先回答：读多写少还是写多读少，单条查询还是范围查询，强一致还是最终一致，数据量多大、增长多快，是否需要审计和回溯。这些答案决定索引、缓存、副本、分区和分片策略。

| 问题 | 影响 |
| --- | --- |
| 读多写少，还是写多读少？ | 索引、缓存、副本策略 |
| 单条查询还是范围查询？ | 索引和存储结构 |
| 强一致还是最终一致？ | 事务和复制方案 |
| 数据量多大？增长多快？ | 分区、分片和归档 |
| 是否需要审计和回溯？ | 历史表和事件表 |

## 建模、主键与索引

建模先找核心实体、关系和一致性边界，避免把展示字段塞进核心表。主键可以选择自增 ID、UUID、雪花 ID 或业务键：自增简单有序但暴露数据量、分片不友好；UUID 全局唯一但索引大、随机写入；雪花 ID 有序唯一但依赖时钟和机器 ID。

规范化和反规范化不是对立，而是顺序问题。先规范化，减少重复、保证一致性；再根据真实查询和性能瓶颈做适度冗余。不要一开始就为“性能”把所有字段冗余，最后写路径到处需要同步。

索引是读性能和写成本的交换。复合索引遵循最左前缀，索引顺序要匹配 `WHERE`、`ORDER BY` 和 `GROUP BY`；覆盖索引可以避免回表；低选择性索引可能没用；索引过多会拖慢插入和更新。用 `EXPLAIN` / `EXPLAIN ANALYZE` 看真实执行计划，不要只看“有没有索引”。

```sql
CREATE INDEX idx_user_status_created
ON orders (user_id, status, created_at);
```

::: tip 先规范化，再反规范化
规范化让数据有一致的唯一来源；反规范化是为了减少 join、提高读性能。先有清晰模型，再根据真实查询做冗余。反过来做，通常会在写入时付出更多同步成本。
:::

## 事务、锁与并发

事务隔离级别决定了脏读、不可重复读和幻读的边界。大多数业务使用 READ COMMITTED 或 REPEATABLE READ；高并发写入用乐观锁或短事务；不要在高并发路径使用长事务；事务内不要做远程调用。

| 级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| READ UNCOMMITTED | 可能 | 可能 | 可能 |
| READ COMMITTED | 否 | 可能 | 可能 |
| REPEATABLE READ | 否 | 否 | 可能（取决于实现） |
| SERIALIZABLE | 否 | 否 | 否 |

乐观锁用版本号或条件更新，适合冲突不高的场景：

```sql
UPDATE orders
SET status = 'PAID', version = version + 1
WHERE id = ? AND version = ?;
```

悲观锁用 `SELECT ... FOR UPDATE`，适合冲突高、必须串行的场景，但要注意锁等待和死锁。无论哪种锁，都要尽量缩短持锁时间，避免在锁内做远程调用和大计算。

## 分片、读写分离与迁移

不要过早分片。先考虑索引优化、归档冷数据、读写分离、缓存和分区表；这些手段不够时，再分库分表。分片键要分布均匀、大多数查询都带这个键、不会造成热点；常见选择是用户 ID 哈希、订单 ID 哈希或时间范围，但时间范围容易产生写热点。

分片后会遇到跨分片 join、跨分片事务、跨分片分页排序、全局唯一 ID 和扩容迁移。解决思路包括：把同一业务键绑定到同一分片、冗余查询表、应用层聚合、接受最终一致、使用全局 ID 服务。

读写分离用主库写、从库读，但要注意复制延迟、读己之写、故障切换和从库数量。对延迟敏感的读，关键路径可以走主库或做降级。

迁移使用 expand-contract：新增字段/表并兼容旧代码；双写或后台回填；切换读路径；确认无旧代码使用后删除旧字段。迁移脚本要可重复执行或有版本记录，大表变更要评估锁表和耗时，先备份，再迁移，有回滚方案。

::: warning 不要过早分库分表
分片会把 join、事务、分页、ID 和迁移复杂度一起放大。先做索引优化、归档、读写分离、缓存和分区表；只有当单库写入、磁盘或连接数真的成为瓶颈时，才考虑分片。
:::

## SQL vs NoSQL

| 类型 | 优点 | 适合 |
| --- | --- | --- |
| 关系型 | 事务、join、约束、成熟 | 核心业务、强一致 |
| 文档型 | 灵活 schema | 内容、配置、半结构化 |
| KV | 简单、高性能 | 缓存、会话、计数 |
| 搜索型 | 全文检索、聚合 | 搜索、日志分析 |
| 列式 | 高吞吐写入、分析 | 时序、日志、分析 |
| 图 | 关系遍历 | 社交、推荐、权限图 |

不要因为“NoSQL 更容易扩展”就放弃关系型数据库。大多数业务的核心数据仍然适合关系型；搜索、日志、缓存等场景再用专用存储。

::: details 小问题：为什么深分页会慢？
`LIMIT 1000000, 20` 需要先扫描并丢弃前一百万行，偏移量越大越慢。更好的方式是游标分页，用上一页最后一个 ID/时间作为条件继续查；或者限制最大可翻页深度。
:::

## Database Design Review 矩阵

| 维度 | 必须回答 | 不满足时怎么办 |
| --- | --- | --- |
| 读写 | 读写模式和规模是否明确？ | 先补基线和压测 |
| 主键 | 主键是否短、稳定、分片友好？ | 重新评估自增/UUID/雪花 |
| 索引 | 是否匹配真实查询和排序？ | 用 `EXPLAIN` 验证并调整 |
| 事务 | 事务是否尽量短？ | 拆事务，移出远程调用 |
| 并发 | 是否需要乐观锁/悲观锁？ | 用版本号或条件更新 |
| 分片 | 是否真的需要分片？ | 先索引、归档、读写分离 |
| 迁移 | 是否可回滚、可回填？ | 用 expand-contract |
| 归档 | 冷数据是否有清理策略？ | 加分区、归档和 TTL |

## 总结

数据库设计可以压缩成三句话：

- 先看读写模式和数据增长，再决定表、索引和事务。
- 先规范化，再根据真实查询反规范化；先优化索引，再考虑分片。
- 事务要短，迁移要可回滚，冷数据要能归档。

如果只能记住一件事：数据库设计不是把表画出来，而是让系统在数据涨十倍后仍然查得动、改得动。
