# 限流

> 限流不是为了拒绝用户，而是为了让系统在过载时仍然能服务核心流量。

系统不会因为“请求多一点”就立刻崩溃，但会先变慢、连接池耗尽、队列堆积，最后在某个环节雪崩。限流的价值，是在过载发生之前主动做减法：保护数据库、缓存、第三方依赖，控制成本，也保证多租户之间的公平性。

限流不是孤立手段。它通常和鉴权、配额、熔断、降级、负载 shedding 一起使用；单靠一个“全局限流”很难同时解决公平性、突发流量和恶意刷接口。

## 本章目标

学完本章，你应该能够：

- 选择固定窗口、滑动窗口、令牌桶或漏桶。
- 设计多维度、多租户的限流配额。
- 用 Redis + Lua 实现分布式限流。
- 设计 429 响应、降级和过载保护。

## 限流到底保护什么

限流的第一目标是保护系统，而不是惩罚用户。它限制进入系统的请求速率，避免突发流量打垮服务；保护数据库、缓存和第三方依赖；防止恶意刷接口；控制成本；在多个租户之间做公平分配。

限流通常和这些手段配合：熔断在下游持续失败时快速失败；降级关闭非核心功能；负载 shedding 在过载时丢弃低优先级请求；排队把请求放入队列等待处理。它们不是互相替代，而是组合使用。

## 算法与取舍

固定窗口按时间窗口计数，简单但边界可能产生双倍突发。滑动窗口按更细粒度统计最近一段时间，精度更高，内存和实现成本也更高。令牌桶以固定速率生成令牌，桶容量决定允许的突发量，适合允许一定突发的 API。漏桶以固定速率流出，适合流量整形，不适合允许突发的场景。并发限制则限制同时处理的请求数，适合保护处理能力有限的下游。

| 算法 | 突发 | 平滑 | 实现复杂度 | 适用 |
| --- | --- | --- | --- | --- |
| 固定窗口 | 边界双倍突发 | 差 | 低 | 简单场景 |
| 滑动窗口 | 较平滑 | 较好 | 中 | 精确限流 |
| 令牌桶 | 允许突发 | 较好 | 中 | API 限流 |
| 漏桶 | 不允许突发 | 好 | 中 | 流量整形 |
| 并发限制 | 不适用 | 好 | 低 | 保护下游 |

::: tip 先选维度，再选算法
只做全局限流，可能被一个大客户打满；只做单用户限流，可能挡不住分布式攻击。常见组合是全局 + 租户 + 用户 + 单接口，再根据业务选择算法和阈值。
:::

## 分布式限流

单机限流简单，但多实例下总量会翻倍。分布式限流通常用 Redis + Lua 保证“读取、判断、更新”原子执行。令牌桶的 Lua 脚本会读取当前令牌数和上次时间，按速率补充令牌，再判断是否足够；key 要按限流维度设计，脚本要短小、无阻塞，时钟要统一。

```lua
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

local data = redis.call('HMGET', key, 'tokens', 'timestamp')
local tokens = tonumber(data[1]) or capacity
local last = tonumber(data[2]) or now

local delta = math.max(0, now - last)
tokens = math.min(capacity, tokens + delta * rate)

if tokens < requested then
  return 0
end

redis.call('HMSET', key, 'tokens', tokens - requested, 'timestamp', now)
redis.call('EXPIRE', key, math.ceil(capacity / rate) + 1)
return 1
```

更稳的结构是“本地令牌桶 + 全局 Redis 配额”：本地限流快速拦截，降低 Redis 压力；全局限流保证集群总量。Redis 故障时要有本地兜底，否则限流层自己会变成新的单点。

## 响应、优先级与过载保护

被限流时返回 `429 Too Many Requests`，并给出 `Retry-After`、`X-RateLimit-Limit`、`X-RateLimit-Remaining` 等响应头。不要返回模糊的 500，否则客户端会误以为系统故障并继续重试。

公平性要通过维度设计实现：核心业务优先、付费用户和免费用户不同配额、读写请求不同策略、批量任务和交互请求隔离、预留突发容量。限流阈值要经过压测，不要拍脑袋；没有压测的阈值，只是另一种形式的猜测。

## Rate Limiting Review 矩阵

| 维度 | 必须回答 | 不满足时怎么办 |
| --- | --- | --- |
| 目标 | 限流保护谁？核心路径是什么？ | 先定义保护对象和优先级 |
| 维度 | 按用户、IP、租户还是接口？ | 组合多个维度，避免单点绕过 |
| 算法 | 是否匹配突发特征？ | 令牌桶/漏桶/滑动窗口重新选型 |
| 分布式 | 多实例总量是否受控？ | Redis 全局配额 + 本地兜底 |
| 响应 | 是否返回 429 和 Retry-After？ | 统一错误码和客户端重试策略 |
| 过载 | 是否与熔断、降级配合？ | 加负载 shedding 和降级开关 |
| 观测 | 是否监控拒绝率和热点 key？ | 接入通过量、拒绝量和延迟指标 |

## 总结

限流的目标是让系统在过载时仍然能服务核心流量：

- 先选保护对象和维度，再选算法和阈值。
- 多实例下必须做全局配额，Redis 故障要有本地兜底。
- 429、Retry-After、优先级和降级，和算法同样重要。

如果只能记住一件事：限流不是“把请求挡掉”，而是“在过载时主动选择服务谁”。
