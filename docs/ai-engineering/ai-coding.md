# AI Coding

> AI 可以更快地写代码，但“能不能合并”仍然取决于规格、测试和 review。

AI 编程最容易制造的一种错觉，是“代码生成得很快，所以开发也很快”。真实情况往往是：生成只占一小段时间，理解需求、准备上下文、检查 diff、运行测试、修复回归和处理 review 才是大头。如果这些环节没有跟上，AI 只是把问题从“写得慢”变成了“改得快、错得也多”。

AI 提高的是产出速度，不是判断力。工程能力越强，越能判断生成代码值不值得保留；工程能力越弱，越容易被“看起来合理”的实现带走。

## 本章目标

学完本章，你应该能够：

- 把模糊需求改写成可验证的任务规格。
- 给 AI 提供必要的代码、测试和错误上下文。
- 用小步实现、测试和 diff 审查控制风险。
- 判断 AI 生成代码是否值得合并。

## AI 改变了什么

AI 擅长生成样板代码、解释陌生代码、补充测试草稿、做局部重构、根据错误日志提出假设、在多个文件之间做机械修改。它不擅长理解未写下来的业务背景、判断架构取舍、保证生成代码正确、处理模糊需求，也不对生产副作用负责。

| AI 更擅长 | AI 不擅长 |
| --- | --- |
| 样板代码、重复模式 | 理解未写下来的业务约束 |
| 解释代码、生成测试草稿 | 判断架构取舍 |
| 局部重构、机械修改 | 保证正确性和边界 |
| 根据日志提出假设 | 对生产副作用负责 |

所以工作方式要变：人负责定义问题和验收标准，AI 负责加速实现和探索，测试和 review 负责确认结果。

## 规格驱动与上下文

在让 AI 写代码前，先写清楚规格：目标、背景、范围、验收标准和不做什么。规格越明确，AI 越容易给出可验证的结果，review 也越有依据。

```markdown
## 目标
修复订单结算重复扣款。

## 背景
客户端超时会重试，当前 settle 没有幂等控制。

## 范围
- 只改 OrderService 和 OrderRepository。
- 不改数据库表结构。

## 验收标准
- 同一个 idempotencyKey 重复调用只扣一次。
- 现有测试全部通过。
- 新增重复请求测试。

## 不做
- 不引入消息队列。
- 不重构整个订单模块。
```

AI 看不到你脑子里的项目背景。相关文件路径、关键类和方法、现有测试、错误日志、数据约束、编码规范、不能修改的模块、期望的验收标准，都要主动提供。任务越具体，AI 越容易给出可验证的结果。

::: tip 规格比 Prompt 更重要
与其反复调整“请认真思考”“务必准确”这类措辞，不如把目标、范围、验收标准和不做什么写清楚。规格是人和 AI 的共同契约，也是 review 的依据。
:::

## 小步实现与验证

推荐流程是：先探索，让 AI 阅读相关代码并说明当前实现；再计划，让它列出修改步骤和风险；人确认计划符合架构和范围；然后一次只改一个逻辑单元；最后编译、测试、lint、类型检查，并检查 diff。

不要让 AI 一次完成“需求分析 + 架构重构 + 实现 + 测试 + 文档”。小步的价值不是慢，而是每一步都能验证、能回滚、能定位问题。每一步都看 diff，而不是只看 AI 的总结；总结可能漏掉它实际改了什么。

测试是 AI Coding 的核心。让 AI 写测试时，要防止测试只验证实现细节、跟着错误实现一起写错、没有断言，或者为了让测试通过而修改测试期望。更好的做法是人先写验收标准或失败测试，AI 实现，运行测试，人 review 测试是否真的验证了行为。

::: warning 不要让 AI 修改测试来“通过”
如果测试失败，正确顺序是先分析是实现错了、测试错了还是需求变了。让 AI 直接改测试期望，会把一个真实缺陷伪装成绿色构建。测试可以改，但必须有明确理由，并经过人 review。
:::

## 审查 AI 生成的代码

AI 生成的代码通常“看起来很合理”，这比明显错误更危险。重点检查 API、库和版本是否真实存在，是否忽略了边界、异常和并发，是否引入了不必要的抽象，是否复制粘贴出重复逻辑，是否破坏现有架构，是否泄露敏感信息，测试是否有效，以及是否符合项目风格。

::: details 小问题：AI 生成的测试可信吗？
不能默认可信。AI 可能写出“能通过但没验证行为”的测试，也可能把实现细节写进断言。判断标准不是测试数量，而是：如果这段逻辑被改坏，测试会不会失败？如果不会，它就不是有效测试。
:::

## Agentic Coding 的边界

AI Coding Agent 可以读取仓库、搜索文件、修改多个文件、运行测试、查看错误并迭代。这提高了自动化程度，也提高了风险：可能修改无关文件、执行危险命令、引入依赖、在没有测试的情况下“宣称完成”，或者在循环中反复试错，产生大量 diff。

控制手段包括：在隔离分支或 worktree 中工作；限制可执行命令；危险操作需要确认；每步检查 diff；设置最大迭代和成本；要求提供测试结果；不让 Agent 直接发布生产。

安全与合规也要提前考虑：不要把密钥、用户数据、未公开代码粘贴到不可信工具；检查 AI 建议的依赖是否可信、许可证是否兼容；防止仓库中的恶意指令影响 Agent；对生成代码做安全扫描；明确代码所有权和责任。

## 如何衡量效果

不要只看“生成了多少行代码”。更有意义的指标是任务交付周期、review 返工率、缺陷率、测试覆盖率变化、构建失败率、开发者主观负担和单位功能成本。如果 AI 让代码产量翻倍，但 review 和返工也翻倍，整体效率可能没有提升。

## AI Coding Review 矩阵

| 维度 | 必须回答 | 不满足时怎么办 |
| --- | --- | --- |
| 规格 | 是否有目标、范围和验收标准？ | 先补规格再让 AI 动手 |
| 上下文 | 是否提供相关文件、测试和错误？ | 补最小充分上下文 |
| 范围 | diff 是否只包含本次任务？ | 拆任务，回滚无关修改 |
| 测试 | 测试是否验证行为并能失败？ | 重写测试，先写失败用例 |
| 安全 | 是否检查 API、依赖和敏感信息？ | 扫描依赖，移除密钥 |
| 回滚 | 是否在隔离分支并可回退？ | 用 worktree/分支和检查点 |
| 责任 | 人是否愿意长期维护这段代码？ | 不合并，重新设计 |

## 总结

AI Coding 的核心，是用工程流程接住更快的产出：

- 规格、上下文、小步实现、测试和 review，一个都不能少。
- AI 生成的代码看起来越合理，越要检查 API、边界和测试有效性。
- Agent 可以提高自动化，但权限、沙箱、预算和回滚必须提前设计。

如果只能记住一件事：AI 可以帮你写代码，但不能替你承担代码进入主干之后的长期责任。
