# Prompt

> 编程 Prompt 的目标不是“让 AI 多写”，而是“让 AI 写出可验证、可 review 的最小变更”。

“帮我优化这个模块”通常不会得到可合并的结果。AI 不知道优化什么、不能改什么、怎样算完成，只能自由发挥。好的编程 Prompt 更像一张任务单：目标、上下文、约束、验收标准和输出要求都写清楚。

## 本章目标

学完本章，你应该能够：

- 用目标、上下文、约束和验收标准描述任务。
- 让 AI 先解释、再计划、最后小步修改。
- 要求最小 diff、测试和验证结果。
- 避免模糊任务、全文件重写和改测试通过。

## 编程 Prompt 的结构

```text
目标：要解决什么问题
上下文：相关文件、错误、测试
约束：不能做什么、必须遵守什么
验收：什么算完成
输出：计划、补丁、测试、说明
```

对于陌生代码，先要求解释：

```text
先阅读 OrderService 和 PaymentCallbackHandler，解释：
1. 支付回调的调用链
2. 幂等校验在哪里
3. 失败时会怎样

不要修改代码。
```

确认理解后再修改。不要让 AI 在没读懂调用链的情况下直接改多个文件。

## 实现、修 Bug 与重构

实现任务要写清目标、相关文件、约束和验收：

```text
目标：
修复支付回调重复扣款。

上下文：
- src/main/java/.../PaymentCallbackHandler.java
- src/main/java/.../OrderService.java
- src/test/java/.../PaymentCallbackHandlerTest.java

约束：
- 不改变现有 API。
- 不新增依赖。
- 只修改上述文件。

验收：
- 同一个 paymentId 重复回调只扣一次。
- 现有测试全部通过。
- 新增重复回调测试。

输出：
1. 先给修改计划。
2. 等我确认后再改。
3. 改完运行测试并贴结果。
```

修 Bug 时必须提供错误信息、复现步骤、期望行为、实际行为和日志。先让 AI 提出 3 个可能原因和验证方法，不要直接改代码。重构则要明确“不改变外部行为”“现有测试通过”“小步修改”“每步运行测试”。

写测试时要求测试名称描述行为、不绑定私有方法、不修改生产代码。代码审查时按正确性、边界、并发、安全、测试有效性输出表格，不要只评价风格。

## 计划、补丁与验证

多文件任务先要计划：需要阅读哪些文件、修改步骤、风险、回滚方式。计划确认后再执行，避免 AI 基于错误理解大改。

要求只输出必要修改、展示 diff、说明每个文件为什么改。不要接受“全文件重写”作为默认方案；全文件重写会让 review 失去重点，也容易夹带无关改动。

改完后明确要求运行 `./gradlew test`、lint、类型检查，贴出命令和结果；如果失败，先分析原因，不要修改测试期望。

::: warning 不要让 AI 修改测试来“通过”
测试失败可能是实现错、测试错或需求变了。直接改测试期望，会把真实缺陷伪装成绿色构建。测试可以改，但必须有明确理由并经过人 review。
:::

## 迭代策略

- 一次只解决一个问题。
- 失败后先分析，不要盲目重试。
- 不在同一轮里混入重构和新功能。
- 每轮检查 diff。
- 不检查 API 是否存在，不合并。

::: details 小问题：Prompt 越长越好吗？
不是。长 Prompt 可能包含更多上下文，也可能包含更多矛盾。有效的是结构化、相关、可执行的信息；无关背景和重复强调只会稀释重点。
:::

## Prompt Review 矩阵

| 维度 | 必须回答 | 不满足时怎么办 |
| --- | --- | --- |
| 目标 | 是否只有一个明确目标？ | 拆成多个任务 |
| 上下文 | 是否提供相关文件、测试和错误？ | 补最小充分上下文 |
| 约束 | 是否说明禁止项和边界？ | 写清不能改什么 |
| 验收 | 是否有可验证标准？ | 改成测试/命令/行为 |
| 计划 | 是否要求先计划？ | 多文件任务先确认方向 |
| 输出 | 是否要求最小 diff 和测试？ | 拒绝全文件重写 |
| 失败 | 是否说明失败处理？ | 先分析，不改测试期望 |

## 总结

编程 Prompt 的核心，是把任务写成可验证的变更说明：

- 目标、上下文、约束、验收和输出，一个都不能少。
- 先解释、再计划、小步修改、运行测试。
- 最小 diff 比“看起来完整”的重写更容易 review。

如果只能记住一件事：AI 写得对不对，取决于你有没有把“怎样算完成”说清楚。
