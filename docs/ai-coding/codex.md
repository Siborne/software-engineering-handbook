# Codex

> Codex 是一个能在终端里读取仓库、修改文件、运行命令的编程 Agent。它的价值在于把“多步任务”变成可执行的循环。

工具能力会随版本变化，具体命令和配置以当前官方文档为准。

Codex 适合做有明确验收标准的多步任务：修一个 bug、补测试、小范围重构、升级依赖、生成文档、跨文件机械修改、排查测试失败。它不适合需求本身不清晰、需要大量业务判断、没有测试保护的大规模重写，以及高风险生产操作。

## 本章目标

学完本章，你应该能够：

- 用 `AGENTS.md` 描述仓库规则和验证命令。
- 把任务拆成可验证的小步。
- 理解审批、沙箱和回滚边界。
- 检查 diff、测试和构建结果。

## 适合什么任务

| 适合 | 不适合 |
| --- | --- |
| 修复有复现步骤的 bug | 需求本身模糊 |
| 补测试、做小范围重构 | 没有测试的大规模重写 |
| 跨文件机械修改 | 高风险生产操作 |
| 排查构建/测试失败 | 需要大量业务判断 |

任务描述要具体：“修复订单结算重复扣款，只改 OrderService 和测试，不改变现有 API，补充重复回调测试，运行 `./gradlew test` 并贴结果。”比“帮我优化订单模块”可靠得多。

## 仓库规则与任务描述

在仓库根目录放 `AGENTS.md`，写清项目是什么、安装/测试/构建命令、代码风格、目录结构、不能修改的路径、提交规范和危险操作。Codex 会优先遵循离目标文件最近的 `AGENTS.md`。

```markdown
# AGENTS.md

## Commands
- install: pnpm install
- test: pnpm test
- build: pnpm build

## Rules
- Do not add dependencies without approval.
- Keep changes small.
- Run tests before claiming completion.

## Boundaries
- Never modify `infra/prod/`.
- Never commit secrets.
```

规则要短、可执行、随代码维护。任务越具体，Codex 越容易给出可验证的结果。

## 审批、沙箱与验证

不同环境可能有不同审批策略：只读、修改文件需确认、命令需确认、完全自动。原则是默认最小权限，危险命令必须确认，生产操作禁止自动执行，在隔离分支或 worktree 中做大改。

Codex 会自己搜索，但你仍然应该提供相关文件路径、错误日志、复现步骤、验收标准和不能修改的范围。复杂任务先探索和解释，再给计划，人确认后小步执行。

::: warning 不读 diff 就等于没 review
不要只看 Codex 的总结。至少检查 `git diff`、测试结果、构建结果、lint/类型检查、是否修改无关文件、是否引入依赖。总结可能漏掉实际改动。
:::

## Codex Review 矩阵

| 维度 | 必须回答 | 不满足时怎么办 |
| --- | --- | --- |
| 任务 | 是否有明确范围和验收？ | 补规格和测试 |
| 上下文 | 是否提供错误、文件和测试？ | 补最小上下文 |
| 计划 | 复杂任务是否先计划？ | 先探索再修改 |
| diff | 是否只改目标文件？ | 回滚无关修改 |
| 验证 | 是否运行测试和构建？ | 失败先分析，不改测试期望 |
| 安全 | 是否限制危险命令和生产？ | 沙箱、确认、最小权限 |

## 总结

Codex 的价值，是把多步编码任务变成可执行、可检查的循环：

- 仓库规则和任务规格，决定它能不能做对。
- 审批、沙箱和回滚，决定它能不能安全地做。
- diff、测试和构建，决定结果能不能合并。

如果只能记住一件事：Codex 可以自主执行，但不能替你承担合并后的责任。
