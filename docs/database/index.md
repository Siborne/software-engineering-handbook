# 数据库

> 数据库选型不是“哪个更先进”，而是“哪种数据模型和一致性模型更适合当前读写模式”。

数据库选型最常见的错误，是拿“扩展性”当唯一标准：关系型还没优化，就急着上 NoSQL；搜索还没做好，就把 Elasticsearch 当主库；缓存还没治理，就把 Redis 当数据源。最后系统有了更多组件，却没有更可靠。

选型应该从数据形状、读写模式、事务边界和一致性要求开始，而不是从产品名开始。

## 本章目标

学完本章，你应该能够：

- 区分关系型、KV、文档、搜索和列式数据库。
- 根据读写模式、事务和查询类型选型。
- 理解索引、事务、复制、分片和缓存的位置。
- 避免把数据库当成万能组件。

## 数据库类型与选型

| 类型 | 代表 | 数据模型 | 适合 |
| --- | --- | --- | --- |
| 关系型 | MySQL、PostgreSQL | 表、行、关系 | 核心业务、事务、复杂查询 |
| KV | Redis、Etcd | key-value | 缓存、会话、配置、计数 |
| 文档 | MongoDB | JSON/BSON 文档 | 半结构化、内容、配置 |
| 搜索 | Elasticsearch、OpenSearch | 倒排索引 | 全文检索、日志分析 |
| 列式 | ClickHouse、Doris | 列存储 | OLAP、日志、指标 |
| 图 | Neo4j | 节点、边 | 社交、推荐、权限图 |
| 时序 | InfluxDB、TimescaleDB | 时间序列 | 监控、IoT |

选型先问：数据结构是强关系还是半结构化，读写比例如何，是否需要事务和多强的一致性，查询是主键、范围、全文还是聚合，数据量和增长速度，是否需要水平扩展，团队是否熟悉运维，以及成本和合规要求。

::: tip 大多数核心数据仍然适合关系型
关系型数据库有事务、约束、join 和成熟生态。不要因为“NoSQL 更容易扩展”就放弃它们。搜索、日志、缓存、时序等场景再用专用存储。
:::

## 核心概念

索引加速读，增加写成本和存储；复合索引要注意顺序；索引要匹配真实查询。事务提供 ACID，但隔离级别、锁和 MVCC 会带来并发代价；事务边界尽量短。复制提高可用性和读扩展，但会带来延迟和故障切换问题。分片解决单库瓶颈，但会放大 join、事务、分页和迁移复杂度。

缓存降低读延迟，但会引入一致性和失效问题；搜索提供全文检索，但索引通常最终一致；列式适合分析，不适合高频点更新。每种能力都有边界，不能指望一个数据库同时做好所有事。

## 学习路径与原则

建议按 MySQL → Redis → MongoDB → Elasticsearch 学习：先理解关系型的事务、索引和复制，再看缓存的失效和高可用，再看文档模型和分片，最后看倒排索引和搜索治理。

设计原则是：先建模，再选型；先单库，再考虑拆分；先优化查询，再换数据库；事务边界清晰；索引匹配查询；缓存不是数据源；搜索索引不是主数据；所有写操作考虑幂等；所有数据考虑备份和恢复。

## Database Review 矩阵

| 维度 | 必须回答 | 不满足时怎么办 |
| --- | --- | --- |
| 数据模型 | 强关系还是半结构化？ | 关系型优先，按查询再选专用库 |
| 读写 | 读多写少还是写多读少？ | 决定索引、缓存和副本策略 |
| 事务 | 是否需要强一致？ | 核心数据用事务型数据库 |
| 查询 | 主键、范围、全文还是聚合？ | 选匹配的索引和存储 |
| 规模 | 数据量和增长多快？ | 先优化、归档，再分片 |
| 运维 | 团队是否能维护？ | 优先托管或成熟方案 |
| 成本 | 存储、带宽和人力成本？ | 冷热分层，按需扩展 |

## 总结

数据库选型的核心，是让数据模型匹配查询和一致性：

- 关系型仍然是大多数核心业务的默认选择。
- 缓存、搜索、文档、列式各有边界，不要互相替代。
- 先优化查询和索引，再考虑分片和换数据库。

如果只能记住一件事：数据库不是越新越好，而是越匹配读写模式和一致性要求越好。
