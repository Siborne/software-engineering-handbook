# Redis

> Redis 快，不是因为它“神奇”，而是因为数据在内存里、命令执行模型简单、数据结构针对场景优化。

Redis 很容易上手，也很容易被滥用。把 Redis 当唯一数据源、所有东西都存 JSON、不设 TTL、用 `KEYS *` 扫生产、大 key 阻塞实例、热 key 打满单分片——这些问题在流量小的时候看不出来，流量一上来就会变成事故。

Redis 的价值是低延迟和丰富的数据结构，不是“无限容量”和“绝对可靠”。理解它的持久化、淘汰、高可用和单线程命令模型，才能用对。

## 本章目标

学完本章，你应该能够：

- 根据场景选择 Redis 数据结构。
- 选择持久化、淘汰和高可用方案。
- 治理大 key、热 key 和慢命令。
- 用监控指标判断 Redis 是否健康。

## 数据结构与场景

| 类型 | 结构 | 典型场景 |
| --- | --- | --- |
| String | 字符串/数字/二进制 | 缓存、计数、分布式锁 |
| Hash | field-value | 对象属性、购物车 |
| List | 双向链表 | 队列、最新列表 |
| Set | 无序集合 | 去重、交集、标签 |
| ZSet | 有序集合 | 排行榜、延时队列 |
| Bitmap | 位图 | 签到、在线状态 |
| HyperLogLog | 基数估算 | UV 统计 |
| Stream | 日志型消息流 | 轻量消息队列 |
| Geo | 地理位置 | 附近的人/店 |

选择原则是用合适结构，不要所有东西都存 JSON 字符串；考虑操作复杂度和内存占用。Key 设计要有命名空间、避免过长、避免用户输入直接拼接、支持批量失效时设计好前缀。

## 持久化、淘汰与高可用

RDB 是定时快照，文件小、恢复快，但可能丢最后一次快照后的数据；AOF 记录写命令，数据更完整，但文件更大、恢复更慢；混合持久化兼顾恢复速度和数据完整性。持久化不等于备份，还需要异地备份和恢复演练。

淘汰策略取决于缓存是否可以丢：`noeviction` 写入报错，`allkeys-lru` 淘汰所有 key，`volatile-lru` 只淘汰有 TTL 的 key，`allkeys-lfu` 按访问频率，`volatile-ttl` 优先淘汰快过期的。没有 TTL 的数据在内存满时会很难处理。

主从复制提供读扩展，但异步复制可能丢数据；Sentinel 做故障转移；Cluster 用 16384 个槽分片，多 key 操作要求同槽。集群提高扩展性，也增加运维和多 key 操作限制。

## 缓存、锁与性能边界

Redis 适合缓存、会话、计数、排行榜、分布式锁和轻量消息。缓存设计要处理穿透、击穿、雪崩、热点 key、大 key 和一致性；分布式锁要使用唯一值、TTL、Lua 释放和续期，必要时加 fencing token。

Redis 命令执行是单线程的（网络 IO 和部分任务多线程），所以慢命令会阻塞所有请求。`KEYS *` 禁止在生产使用；大 key 的 `HGETALL`、`SMEMBERS`、`ZRANGE`、`DEL` 都可能阻塞；Lua 脚本要短小、无阻塞。

::: warning 生产环境不要使用 `KEYS *`
`KEYS` 会遍历整个 keyspace，数据量大时可能阻塞 Redis 数秒甚至更久。按模式查找用 `SCAN`，控制每次返回数量；批量删除用业务前缀、异步任务和限流。
:::

Pipeline 批量发送命令，减少网络往返，但不保证原子性；Lua 在 Redis 内原子执行，适合限流、锁释放和原子计数；`MULTI/EXEC` 提供命令队列，但不支持回滚到中间状态。复杂原子逻辑优先 Lua。

::: details 小问题：大 key 只是 value 很大吗？
不只看字节数，还要看集合元素数量、访问频率和删除成本。一个大 Hash、大 Set 或大 List，即使总字节不算夸张，也可能在读取、删除和网络传输时阻塞 Redis。治理方式是拆分、压缩、异步删除，避免一次性读取整个集合。
:::

## 监控与选型

监控要覆盖命中率、QPS、P99 延迟、内存使用、淘汰数量、连接数、大 key/热 key、主从延迟和慢查询。命中率高但回源 QPS 仍然高，可能说明缓存的是低价值数据；淘汰数量突然上升，通常意味着内存不够。

Redis 不是唯一数据源，也不适合大对象存储、复杂事务和强一致核心账务。它最适合“可以丢、可以重建、低延迟”的数据；需要持久可靠的核心数据，仍然应该放在关系型数据库。

## Redis Review 矩阵

| 维度 | 必须回答 | 不满足时怎么办 |
| --- | --- | --- |
| 适用性 | 数据是否适合放 Redis？ | 核心数据回数据库 |
| 结构 | 是否选对数据结构？ | 按操作和内存重新选型 |
| TTL | 是否设置过期和淘汰策略？ | 加 TTL、maxmemory 和淘汰 |
| 大 key | 是否拆分、异步删除？ | 拆分、压缩、SCAN 删除 |
| 热 key | 是否有本地缓存/分片？ | 热点探测和请求合并 |
| 高可用 | 主从/集群故障如何降级？ | Sentinel/Cluster + 兜底 |
| 观测 | 是否监控命中率、内存和延迟？ | 接入指标和慢查询 |

## 总结

Redis 的核心，是用内存和数据结构换取低延迟：

- 用对数据结构，设置 TTL 和淘汰策略，别把它当唯一数据源。
- 大 key、热 key 和慢命令，是 Redis 最常见的性能杀手。
- 持久化、主从、Sentinel/Cluster 要按数据重要性设计。

如果只能记住一件事：Redis 快，但它的边界很清楚；越过边界，它就会从加速器变成故障源。
