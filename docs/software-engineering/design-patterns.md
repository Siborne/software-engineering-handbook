# 设计模式

> 设计模式是前人总结的“在特定问题下的可复用结构”，不是可以到处套用的模板。

设计模式最容易带来的副作用，是让简单问题变复杂。一个只有两个分支的计价逻辑，被拆成策略接口、工厂、注册表和配置类；一个简单对象，被套上三层建造者和抽象工厂。代码看起来“很设计”，但读者需要跳转五个文件才能知道发生了什么。

模式的价值在于命名和复用：它让团队用共同语言描述结构，也让你在重构时知道有哪些可选方向。但它不是目标，解决问题才是。

## 本章目标

学完本章，你应该能够：

- 判断一个场景是否真的需要设计模式。
- 区分创建型、结构型和行为型模式。
- 用策略、工厂、适配器等解决常见设计问题。
- 识别为了模式而模式的过度设计。

## 模式解决什么问题

| 类型 | 关注点 | 常见模式 |
| --- | --- | --- |
| 创建型 | 如何创建对象 | 工厂方法、抽象工厂、建造者、单例、原型 |
| 结构型 | 如何组合对象和类 | 适配器、装饰器、代理、外观、组合、桥接 |
| 行为型 | 对象之间如何协作 | 策略、观察者、模板方法、责任链、状态、命令、迭代器、中介者 |

模式不是按类型背出来的。真正要记的是“它解决了什么变化”：策略解决算法可替换，工厂解决创建逻辑复杂，适配器解决接口不兼容，装饰器解决职责动态叠加，观察者解决状态变化通知，模板方法解决流程骨架固定、局部步骤可变。

## 常用模式与场景

策略模式适合计价、折扣、路由、风控等规则会持续增加，且不同分支行为差异较大的场景。它把算法从调用方剥离出来，新增策略不需要修改调用方。

```java
interface PricingStrategy {
    BigDecimal calculate(Order order);
}
```

工厂模式适合创建逻辑复杂或调用方不应该知道具体实现的场景；建造者适合参数多、可选参数多、需要保证不可变性的对象；适配器适合接入第三方 SDK 或隔离新旧接口；装饰器适合日志、缓存、限流、重试等横切能力；观察者适合领域事件、通知和审计；模板方法适合导入、导出、批处理等固定骨架；责任链适合审批、过滤器和风控规则；状态模式适合订单、支付、工单等状态机；代理适合懒加载、权限控制和远程调用。

| 问题 | 优先考虑 |
| --- | --- |
| 多种算法/规则可替换 | 策略 |
| 创建逻辑复杂或需要隐藏实现 | 工厂 |
| 参数多、构建过程复杂 | 建造者 |
| 第三方接口不兼容 | 适配器 |
| 动态叠加日志、缓存、限流 | 装饰器 |
| 状态变化通知多个订阅者 | 观察者 |
| 固定流程骨架，局部步骤可变 | 模板方法 |
| 请求经过多个处理者 | 责任链 |
| 状态转换复杂 | 状态 |
| 控制对象访问 | 代理 |

::: details 小问题：策略模式和 switch 怎么选？
只有两三个稳定分支、逻辑很短时，switch 更直观；分支会持续增加、每个分支行为差异大、需要独立测试时，策略更合适。不要为了“可扩展”提前拆出十几个类。
:::

## 什么时候不该用模式

只有一个实现，而且短期内不会增加时，不要抽象；逻辑只有两三行，直接写更清楚；引入模式后，调用链变长但收益不明显；你无法用一句话说清这个模式解决了什么问题；你只是为了“看起来更高级”。

先写简单代码，等到变化真的出现，再用模式消除重复和耦合。这就是 YAGNI 和“三次原则”的实践。

::: warning 为了模式而模式，比重复代码更难维护
模式增加的是间接层。没有真实变化支撑的抽象，会让读者在多个文件之间跳转，却找不到业务重点。模式应该消除复杂度，而不是转移复杂度。
:::

## 常见误区

把模式当目标，会为了用策略而拆出十几个类；把单例当全局变量，会隐藏依赖；把工厂当万能入口，会增加复杂度；把设计模式当架构，会忽略系统边界和部署问题；忽略语言特性，会把 Java 的策略模式生搬到函数式语言里。

## Pattern Review 矩阵

| 维度 | 必须回答 | 不满足时怎么办 |
| --- | --- | --- |
| 问题 | 这个模式解决的具体问题是什么？ | 说不清就不要引入 |
| 必要性 | 不用模式会带来什么实际问题？ | 先用简单实现 |
| 变化 | 是否真的存在多种实现或持续变化？ | 避免过早抽象 |
| 调用方 | 是否只依赖稳定接口？ | 调整依赖方向 |
| 复杂度 | 间接层是否让代码更难理解？ | 内联回简单实现 |
| 替代 | 是否有更简单的语言特性？ | 优先函数、枚举、组合 |

## 总结

设计模式的核心，是用共同结构解决真实变化：

- 模式不是目标，能说清“解决什么问题”才值得用。
- 策略、工厂、适配器、装饰器等模式各有适用边界。
- 简单场景优先直接写，变化出现后再抽象。

如果只能记住一件事：好的设计不是用了多少模式，而是读代码的人不需要跳转五个文件才能理解业务。
