# 工程实践

> 代码质量不是个人习惯，而是团队流程的结果。

一个团队可以偶尔靠某个高手写出好代码，但很难靠个人自觉长期维持质量。没有 CI，测试就会被跳过；没有 review，风格和边界就会漂移；没有技术债记录，临时方案会永久留下；没有文档，知识只存在某个人脑子里。

工程实践的作用，是把“正确的做法”变成“默认会发生的事情”：不是靠某个人记得写测试，而是流水线自动跑；不是靠 reviewer 提醒格式，而是 formatter 自动检查。

## 本章目标

学完本章，你应该能够：

- 把代码质量放进团队流程，而不是依赖个人自觉。
- 设计 Definition of Done 和质量门禁。
- 管理技术债、文档、依赖和发布。
- 让 AI 辅助研发保持可控和可审计。

## 工程实践在解决什么

工程实践覆盖 Definition of Done、质量门禁、技术债、文档、依赖管理、发布回滚、事故复盘和 AI 协作。它不直接写业务代码，但决定了业务代码能不能长期维护。

个人能力决定代码的上限，工程实践决定团队的下限。一个团队如果依赖英雄主义救火，迟早会被英雄主义反噬。

## Definition of Done 与质量门禁

一个任务“完成”不只是代码能跑。建议团队约定 Definition of Done：代码实现需求并通过自我 review，关键行为有测试，格式/静态检查/类型检查通过，CI 通过，必要的日志和错误处理已加入，配置和数据库变更可回滚，文档已更新，风险和回滚方式已说明。

质量门禁把能自动检查的事情交给工具：

| 门禁 | 作用 | 典型工具 |
| --- | --- | --- |
| 格式化 | 消除格式争论 | Spotless、Prettier、Black、gofmt、rustfmt |
| 静态检查 | 发现空 catch、未使用变量、原始类型 | Checkstyle、ESLint、Ruff、Clippy、staticcheck |
| 类型检查 | 编译期发现类型错误 | `javac`、`tsc`、mypy、pyright |
| 单元测试 | 验证核心逻辑 | JUnit、Vitest、pytest |
| 集成测试 | 验证数据库、消息队列、外部依赖 | Testcontainers、Spring Boot Test |
| 构建 | 确认产物可生成 | Gradle、Maven、pnpm、Cargo |
| 安全扫描 | 发现依赖漏洞和敏感信息 | Dependabot、Trivy、Semgrep、gitleaks |
| Code Review | 检查设计、正确性和可维护性 | 人工 review |

原则是：能在本地发现的不要留到 CI，能在 CI 发现的不要留到线上，门禁失败必须修复，不能长期“红着合并”。对确需豁免的情况，要记录原因和期限。

::: warning 门禁不是装饰
如果 CI 红了也能合并，门禁就失效了。失败要么立即修，要么明确豁免并限期处理；否则团队会学会忽略它。
:::

## 技术债、文档与依赖

技术债不一定是坏事。为了赶上线做出的临时方案，是有意识的技术债；因为缺乏设计、测试或规范产生的混乱，是无意识的技术债。有意识的技术债要记录在 backlog，设定触发条件；无意识的技术债要在日常开发中持续修复；已经影响交付的腐烂技术债，要单独立项、分阶段偿还。

技术债清单至少记录：问题是什么、影响哪些功能或团队、不处理最坏会发生什么、偿还成本大概多少、什么时候必须处理。不要把所有“代码不够漂亮”都叫技术债，技术债应该和交付风险、维护成本或架构演进相关。

文档不需要很多，但关键信息必须可查：README 说明项目是什么、如何启动和测试；ADR 记录重要技术决策；Runbook 说明线上故障如何排查和回滚；API 文档说明契约、错误码和示例。判断标准是：一个不熟悉项目的人，能否靠文档完成启动、测试和基本排障。

依赖管理要用锁文件保证构建可复现，固定运行时和包管理器版本，定期更新依赖，关注安全公告和许可证，引入新依赖前评估维护活跃度、体积、安全记录和替代方案，删除不再使用的依赖。

## 发布、事故与 AI 协作

发布前确认数据库变更兼容旧版本，使用灰度、开关或分批发布降低风险，每次发布都有回滚方案。发布后观察错误率、延迟、饱和度和业务指标；回滚不是失败，而是工程能力。

事故复盘的目标是改进系统，而不是追究个人。好的复盘包含时间线、影响、根因、处理过程和改进项；改进项要有负责人和截止时间。避免“某人操作失误”就结束，也避免只写“加强培训”而没有具体机制。

AI 可以生成代码、测试草稿、review 建议和排障假设，但人必须验证正确性、边界、安全和架构一致性。使用原则是：不把密钥、用户数据和未公开代码粘贴到不可信工具；一次给 AI 一个清晰、可验证的小任务；要求说明假设和不确定点；对 AI 生成代码执行同样的测试、review 和门禁；最终责任人始终是人。

## Engineering Practice Review 矩阵

| 维度 | 必须回答 | 不满足时怎么办 |
| --- | --- | --- |
| DoD | “完成”的定义是否清晰？ | 写清测试、文档、发布和回滚要求 |
| 门禁 | 关键检查是否自动执行？ | 接入 CI，禁止红着合并 |
| 技术债 | 是否有记录和偿还计划？ | 建 backlog，设定触发条件 |
| 文档 | 新人能否靠文档启动和排障？ | 补 README、ADR 和 Runbook |
| 依赖 | 是否锁定、更新和安全扫描？ | 加锁文件、Dependabot 和审计 |
| 发布 | 是否灰度、可回滚、可验证？ | 加开关、探针和回滚演练 |
| 复盘 | 是否有无责复盘和改进项？ | 记录时间线、根因和负责人 |
| AI | 是否有验证和权限边界？ | 人工 review、测试和脱敏 |

## 总结

工程实践的核心，是把质量变成默认流程：

- Definition of Done 和质量门禁，让“完成”有明确标准。
- 技术债、文档、依赖和发布，决定系统能不能长期维护。
- AI 可以提高效率，但不能替代测试、review 和责任。

如果只能记住一件事：不要依赖某个人记得做对，要让流程让做对成为默认选项。
