# 技术成长

> 技术成长不是“年限增长”，而是“能独立处理的问题复杂度在增长”。

## 本章目标

学完本章，你应该能够：

- 判断自己当前的能力阶段。
- 平衡技术深度和工程广度。
- 用 ownership 和影响力推动更复杂的问题。
- 设计可持续的成长节奏。

## 能力阶段

| 阶段 | 核心特征 | 需要证明 |
| --- | --- | --- |
| 初级 | 在明确任务下完成开发 | 代码正确、可维护 |
| 中级 | 独立负责模块 | 能拆解、能排障、能交付 |
| 高级 | 负责复杂系统或跨团队项目 | 架构取舍、稳定性、影响力 |
| 专家/Staff | 定义方向、解决组织级问题 | 技术战略、跨团队推动 |

职级名称因公司而异，重点看能力变化。

## 技术深度

深度不是“知道更多 API”，而是：

- 理解原理。
- 能定位复杂问题。
- 能判断方案边界。
- 能做性能优化。
- 能写高质量代码。

形成深度的方法：

1. 选一个方向。
2. 读源码和官方文档。
3. 做真实项目。
4. 排查线上问题。
5. 写总结和分享。

## 工程广度

广度不是“什么都浅尝”，而是：

- 理解上下游。
- 能做系统设计。
- 能处理稳定性、性能、安全。
- 能评估成本和复杂度。
- 能跨团队协作。

建议顺序：

```mermaid

    A["语言 / 框架"] --> B["数据库 / 缓存"] --> C["消息 / RPC"] --> D["系统设计"]
    D --> E["测试 / CI/CD / 可观测性"] --> F["安全 / 成本"] --> G["AI 工程"]
```

## Ownership

高级工程师的重要标志是 ownership：

- 不只完成分配的任务。
- 主动发现问题。
- 对结果负责。
- 推动跨团队依赖。
- 处理模糊需求。
- 复盘并改进。

Ownership 不等于“什么都要自己做”，而是“确保事情被解决”。

## 影响力

影响力可以来自：

- 高质量代码。
- 技术方案。
- 故障排查。
- Code Review。
- 文档和分享。
- 带新人。
- 开源。
- 跨团队推动。

让工作可见：

- 写清问题、方案、结果。
- 用指标证明。
- 做复盘。
- 分享经验。

## 反馈

主动获取反馈：

- Code Review。
- 主管 1:1。
- 同事评价。
- 面试。
- 用户反馈。
- 线上指标。

反馈要具体：

> “我这次方案评审讲得不够清楚，下次应该先讲结论和取舍，再讲细节。”

不要：

- 只问“我表现怎么样”。
- 听完不行动。
- 对负面反馈防御。

## 技术判断

高级工程师要能判断：

- 什么时候用新技术。
- 什么时候保持简单。
- 什么时候重构。
- 什么时候还技术债。
- 什么时候停止优化。
- 什么风险可以接受。

判断依据：

- 业务价值。
- 复杂度成本。
- 团队能力。
- 维护成本。
- 失败影响。

## 可持续成长

- 保证睡眠和运动。
- 避免长期透支。
- 设定学习节奏。
- 接受阶段性重点。
- 不盲目比较。
- 定期复盘。

> 成长是长期复利，不是短期燃烧。

## 成长指标

- 能独立负责的系统复杂度。
- 解决的问题影响范围。
- Code Review 质量。
- 故障处理能力。
- 方案被采纳率。
- 带人和分享。
- 交付稳定性。

不要只用：

- 代码行数。
- 加班时长。
- 学习课程数量。

## 常见错误

- 只做熟悉的事。
- 频繁换方向。
- 只学不用。
- 不总结。
- 不主动沟通。
- 把加班当成长。
- 只追求职级，不提升能力。
- 不接受反馈。
- 不关注业务价值。

## 总结

技术成长的核心，是让可解决的问题变复杂、让判断更可信：

- 深度靠原理和排障，广度靠系统和协作。
- Ownership 是高级工程师的分水岭。
- 成长要可持续，不是短期燃烧。

如果只能记住一件事：每年问自己“我能独立解决比去年更复杂的问题吗”。
