# RPC

> RPC 的目标是“像调用本地方法一样调用远程服务”，但网络永远不会像本地调用一样可靠。

RPC 把本地调用包装成远程请求，让代码看起来像在调用一个普通方法。但本地调用不会超时、不会丢包、不会部分成功，远程调用会。忽略这个差异，就会写出“以为调用成功、实际只成功了一半”的代码。

理解 RPC，要同时看协议、服务发现、超时重试和幂等。任何一个环节没设计好，远程调用都会从“抽象”变成“故障源”。

## 本章目标

学完本章，你应该能够：

- 解释 RPC 的序列化、协议和传输链路。
- 设计服务发现、负载均衡和健康检查。
- 设置超时、重试、熔断和幂等。
- 用 traceId 和指标排查远程调用问题。

## RPC 到底发生了什么

调用方通过 Stub 发起请求，序列化后经网络传给服务端，服务端反序列化并执行，再把结果序列化返回。

```mermaid
flowchart LR
    A["Client Stub"] --> B["序列化"] --> C["网络"] --> D["服务端"] --> E["反序列化"]
    E --> F["执行"] --> G["序列化结果"] --> H["网络"] --> I["Client Stub"]
```

核心组件包括 Stub、序列化、协议、传输、服务发现、负载均衡和治理。RPC 与 HTTP 不是对立的：gRPC 基于 HTTP/2 + Protobuf，HTTP + JSON 也是常见的远程调用方式。选择时看性能、跨语言、schema 演进、可读性和生态。

## 序列化、协议与服务发现

JSON 可读、通用，但体积大、性能一般；Protobuf 紧凑、跨语言、强 schema，适合内部服务；Hessian 在 Java 生态常用，但跨语言较弱。schema 演进要新增可选字段、不要随意改类型、不要复用已删除的字段编号，客户端和服务端要能灰度共存。

gRPC 强契约、支持流式，适合内部服务；Dubbo 在 Java 生态治理能力丰富；HTTP + JSON 简单通用，适合对外 API。服务发现用注册中心、DNS 或 Service Mesh，需要处理实例上下线、健康检查、灰度、多机房和注册中心故障。负载均衡有轮询、随机、加权、最少连接、一致性哈希和就近访问；长连接下负载可能不均，需要健康检查和摘除慢实例。

## 超时、重试与幂等

每个远程调用都必须有超时：连接超时、读超时、总超时和重试总预算。超时要小于上游请求的剩余时间，不要无限等待。

重试只针对可恢复错误：网络超时、连接失败、限流/临时不可用。参数错误、业务拒绝和非幂等写操作不应该重试。重试要指数退避、加抖动、限制次数、有总预算。

::: warning 不要重试非幂等写操作
创建订单、扣款、退款这类操作，如果没有幂等键，重试可能造成重复副作用。重试前先问：这次调用重复执行一次，结果是否仍然正确？
:::

写操作重试前必须幂等：请求 ID、业务唯一键、幂等表、状态机。调用方生成 idempotency key，服务端按 key 去重，数据库唯一约束兜底。

熔断和降级用于下游持续失败时快速失败，避免雪崩；限流保护下游；可观测性记录服务名、方法名、traceId、耗时、状态码、重试次数、序列化大小和错误类型。

## 可观测性与治理

每次调用要能回答：哪个服务、哪个方法、耗时多少、是否重试、失败原因是什么、调用链上下游是谁。指标看 QPS、P95/P99 延迟、错误率、超时率、重试率和熔断次数。

接口要有版本管理，契约要可演进；同步调用链不要过长，否则一个下游抖动会放大成整条链路超时。对关键依赖设置隔离、超时和降级，避免一个非核心服务拖垮核心路径。

::: details 小问题：gRPC 和 HTTP + JSON 怎么选？
内部服务、强契约、高性能和流式场景优先 gRPC；对外 API、调试友好、跨团队通用场景优先 HTTP + JSON。关键不是协议“更高级”，而是契约、演进和治理是否匹配团队能力。
:::

## RPC Review 矩阵

| 维度 | 必须回答 | 不满足时怎么办 |
| --- | --- | --- |
| 契约 | 接口是否清晰、可演进？ | 加 schema 版本和兼容规则 |
| 序列化 | 格式是否匹配性能和跨语言需求？ | JSON/Protobuf/Hessian 重新选型 |
| 超时 | 是否有连接/读/总超时？ | 设置超时和剩余时间预算 |
| 重试 | 是否只重试可恢复错误？ | 限制错误类型、次数和退避 |
| 幂等 | 写操作重复调用是否安全？ | 加 idempotency key 和唯一约束 |
| 治理 | 是否有熔断、限流和降级？ | 加治理策略和隔离 |
| 观测 | 是否有 traceId 和指标？ | 接入 tracing 和延迟/错误率 |

## 总结

RPC 的核心，是承认远程调用和本地调用不一样：

- 序列化、协议、服务发现和负载均衡决定调用能不能到达。
- 超时、重试、幂等和熔断决定失败时会不会放大。
- traceId 和指标决定出问题时能不能定位。

如果只能记住一件事：远程调用必须假设网络会慢、会断、会重复；重试之前，先确保操作幂等。
