# 如何提问

> 一个好问题，往往已经包含了一半的答案。

很多人以为，提问能力体现在“问得快”。真正困难的，是在自己还没有完全想清楚时，仍然能把问题描述到别人可以接手。你贴出一句“为什么我的代码跑不起来”，对方看到的不是一个问题，而是一片没有边界的现场：不知道你想做什么，不知道你看到了什么，也不知道你已经排除了什么。

技术提问不是把思考外包。它更像一次交接：你把目标、现场和已经走过的路交给对方，让对方不用从零开始猜。下面讨论的是一套通用的提问方式；无论对方是同事、开源社区，还是 AI，判断标准都一样：对方能否理解、复现并继续推进。

## 本章目标

学完本章，你应该能够：

- 用一句话说清要解决的问题和期望结果。
- 提供足以复现问题的最小上下文，而不是倾倒整个项目。
- 先读报错和做基础排查，再决定向谁求助。
- 把一次回答变成有效追问，并验证最终结论。

## 提问是在交付上下文

一个可回答的技术问题，通常包含四类信息：『目标』、『现场』、『边界』和『请求』。目标是你想让程序完成什么；现场是实际发生了什么，包括报错、日志、版本和运行环境；边界是你已经检查过什么、排除了什么；请求则是你希望对方帮你做哪一类判断，是定位根因、评审方案，还是解释一个概念。

这四类信息不需要写成公文。下面两句话的差别，不在长度，而在对方能否开始工作：

> 我的代码跑不起来，怎么办？

> Spring Boot 3.5 启动时报 `BeanCreationException`，我希望服务监听 8080，实际在创建 `UserRepository` 时启动失败。Java 21，依赖版本如下，完整堆栈的前 30 行如下。我已经确认数据库能连接，也试过清理 Maven 缓存，但错误仍然出现。请问应该先检查哪个 Bean 的注入链？

后一句仍然可以更短，但它已经给了对方一个可验证的入口。提问时不必把所有细节都写出来，但必须让回答者知道：问题发生在哪一层，什么现象是意外的，以及你希望他帮你缩小哪一段不确定性。

::: tip 提问前先做一次“对方视角”检查
如果我是对方，只看到这段文字，能不能判断问题出在哪？如果不能，缺的通常是目标、现场或已尝试的方案，而不是“更礼貌的开场白”。
:::

## 先让问题可以被复现

『最小可复现示例』是技术提问里最值得养成的习惯。它的意思不是把项目删到只剩一行，而是保留能够触发问题的最少代码、配置和数据，同时去掉与问题无关的业务逻辑、密钥和噪音。能稳定复现的问题，才有稳定的答案；不能复现的问题，往往只能得到猜测。

复现材料通常包括：运行环境和版本、最小代码或配置、实际结果、期望结果，以及你已经尝试过的操作。贴日志时，保留第一条异常、关键调用链和真正的错误信息，比粘贴几千行日志更有用。贴代码时，优先给文本而不是只发截图；对方需要搜索、复制和运行，截图会让排查成本变高。

::: details 可直接复制的提问模板
```text
我想完成：
运行环境：
实际结果：
期望结果：
最小复现步骤 / 代码：
关键报错：
已经尝试：
我希望你帮我判断：
```
:::

这个模板不是要你每次填满所有格子。它的作用是提醒你：一个问题至少要能让对方区分“你想要什么”和“你看到了什么”。如果某一项暂时不知道，也可以明确写“这一项还没确认”，不要用模糊描述把它藏起来。

::: warning 不要把“完整”理解成“全部”
完整不等于把整个仓库、整份日志和所有背景都贴出来。对回答者真正有用的完整，是围绕问题保留足够证据，而不是把筛选信息的成本转移给对方。涉及密钥、token、客户数据和公司内部代码时，先脱敏或改用最小示例。
:::

## 先读报错，再决定问谁

很多初学者看到报错的第一反应，是立刻复制给 AI 或同事。更有效的顺序是先用几分钟读一遍：第一条异常是什么，异常类型和消息说明了什么，堆栈里哪一行最接近你的代码，最近改动了什么。很多时候，报错已经把范围缩得很小，只是被后面的连锁异常淹没了。

读完之后再决定问谁。概念不清楚，可以问教材、文档或 AI；环境配置和项目约定，优先查项目文档和同事；涉及线上数据、权限或不可逆操作，应该找能对结果负责的人。AI 适合帮你解释报错、提出假设和设计验证步骤，但它不应该替代你确认版本、运行代码和检查最终结果。

提问时也要说清楚你要的是哪一种帮助。是“告诉我这条异常通常由什么引起”，还是“帮我判断这三个根因里哪个最可能”，还是“请评审我的修复方案”。问题越接近一个可执行的判断，回答就越不容易变成泛泛而谈。

::: details 小问题：应该先自己查多久再问？
没有统一分钟数。判断标准不是“查了多久”，而是“我是否已经形成了一个可以验证的假设”。如果你只是反复搜索同一句话，没有产生新的检查动作，就该带着已有信息去问；如果你还没有读第一条异常，也没有跑过一次最小验证，先补上这一步通常更快。
:::

## 好问题与坏问题

坏问题通常不是不礼貌，而是没有给对方一个可以落脚的地方：

> 我的 Java 项目启动不了，怎么办？

它缺少目标、环境、报错、期望结果和已尝试方案。对方只能反问五六轮，才能知道你到底在说什么。

好问题会把回答者带到现场：

> 我在本地启动一个 Spring Boot 3.5 项目，执行 `mvn spring-boot:run` 后服务没有监听 8080。控制台第一条异常是 `BeanCreationException`，指向 `UserRepository` 的依赖注入；完整堆栈的关键部分如下。Java 21，数据库连接已确认正常，我也清理过 Maven 缓存。我的判断是某个 Bean 的构造依赖没有满足，但不确定应该先看配置还是看依赖图。请问下一步最值得验证什么？

两段话的差别不只是“信息更多”。好问题明确了期望结果和实际结果，给出了最小证据，也说明了自己的假设。即使这个假设是错的，对方也能根据你的判断路径指出偏差，而不是从零开始审问。

## 追问与验证

得到回答不等于问题结束。一个有效的追问，应该围绕“证据”和“边界”展开：这个结论依据什么？在什么条件下不成立？我接下来能做哪一个最小实验来验证？如果对方的回答和你的现场不一致，不要急着争论，先把不一致的地方变成下一个问题。

《提问的艺术》讨论的是商业和人际沟通，但它有一个视角同样适用于技术求助：问题应该推动对话，而不是把对方逼进一个只能回答“是”或“否”的角落。一次只推进一个未知，通常比一口气抛出十个问题更容易得到高质量回答。

问题解决后，最好回到对话里补一句结果：真正的原因是什么，哪个验证步骤确认了它，最后改了什么。这样做不仅是对回答者的反馈，也是在为下一次遇到同类问题留下可复用的线索。

## 总结

提问的核心，是降低对方理解问题的成本：

- 先说目标和期望结果，再说实际现象；让对方知道你要解决什么。
- 提供最小可复现的上下文，保留关键证据，删掉无关信息。
- 先读报错、形成假设，再决定问人、查文档还是用 AI。
- 得到回答后继续追问证据和边界，并回报最终验证结果。

如果只能记住一件事：不要问“为什么我的代码跑不起来”，要给出能让对方复现、判断和继续追问的现场。
